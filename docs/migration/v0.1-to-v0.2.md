# Migrating from v0.1 to v0.2

This guide covers every breaking change between **v0.1.0** and **v0.2.0** of the PayStream
contracts, with before/after examples for each one.

- **Who needs this guide:** anyone calling the `StreamContract` or `TokenContract` directly —
  off-chain indexers, payroll back-ends, CLI tools, and automation scripts.
- **What you need to do:** update the call sites listed below. Everything else in v0.2 is
  additive and needs no changes.
- **Related:** [API reference](../api-reference.md) · [Events schema](../events-schema.md) ·
  [Upgrade guide](../upgrade-guide.md) · [CHANGELOG](../../CHANGELOG.md)

---

## TL;DR — breaking changes at a glance

| # | Change | Contract | Action |
|---|--------|----------|--------|
| 1 | `create_stream` takes a new required `low_balance_threshold` argument | Stream | Add the argument at every call site |
| 2 | `pause_contract` / `unpause_contract` take a `nonce` argument | Stream | Read `admin_nonce()` and pass it |
| 3 | `upgrade` takes a `nonce` argument | Stream | Read `admin_nonce()` and pass it |
| 4 | `burn` no longer takes an `admin` argument | Token | Drop the argument, authorise as holder or spender |
| 5 | `mint` takes a new required `nonce` argument | Token | Read `admin_nonce()` and pass it |
| 6 | `approve` takes a new required `expiration_ledger` argument | Token | Pass the last ledger the allowance is valid for |
| 7 | `initialize` can no longer be called twice | Stream | Only call it once per deployment |
| 8 | `Stream` has two new fields | Stream | Update struct decoders |
| 9 | Panic strings were replaced by `E###` error codes | Stream + Token | Match on the error code, not the prose |
| 10 | Event topics are prefixed with the schema version `v1` | Stream | Update the event parser |
| 11 | `create_streams_batch` is capped at 50 streams | Stream | Split larger batches |
| 12 | Batch panic messages are prefixed with the stream index | Stream | Strip the `stream[N]: ` prefix before matching |

**No function was removed in v0.2.** Every v0.1.0 entry point still exists, and the only
removed *parameter* is the `admin` argument of the token `burn` function (change 4), which
was replaced by holder/spender authorisation.

---

## 1. `create_stream` takes a new required argument

`create_stream` gained a `low_balance_threshold` argument. It is the amount of remaining
deposit below which the contract emits a `low_balance` event so the employer can be alerted.
Passing `None` disables the alert, which is the behaviour of v0.1.0.

**Before (v0.1.0)**

```rust
let stream_id = client.create_stream(
    &employer,
    &employee,
    &token,
    &deposit,
    &rate_per_second,
    &stop_time,
);
```

**After (v0.2.0)**

```rust
let stream_id = client.create_stream(
    &employer,
    &employee,
    &token,
    &deposit,
    &rate_per_second,
    &stop_time,
    &None, // low_balance_threshold: Option<i128> — None disables the alert
);
```

**Before (v0.1.0)**

```bash
stellar contract invoke --id $CONTRACT -- create_stream \
  --employer $EMPLOYER --employee $EMPLOYEE --token_address $TOKEN \
  --deposit 1000000 --rate_per_second 10 --stop_time 0
```

**After (v0.2.0)**

```bash
stellar contract invoke --id $CONTRACT -- create_stream \
  --employer $EMPLOYER --employee $EMPLOYEE --token_address $TOKEN \
  --deposit 1000000 --rate_per_second 10 --stop_time 0 \
  --low_balance_threshold 100000
```

The threshold can be changed later with `set_low_balance_threshold(employer, stream_id, threshold)`
and `0` disables it again.

## 2. `pause_contract` and `unpause_contract` take a `nonce`

Contract-wide pause and unpause are now nonce-protected, so a replayed transaction cannot
toggle the contract. The nonce is read with `admin_nonce()` and is consumed by the call.

**Before (v0.1.0)**

```rust
client.pause_contract();
client.unpause_contract();
```

**After (v0.2.0)**

```rust
let nonce = client.admin_nonce();
client.pause_contract(&nonce);

// The nonce is consumed, so read a fresh one before the next admin call.
let nonce = client.admin_nonce();
client.unpause_contract(&nonce);
```

**Before (v0.1.0)**

```bash
stellar contract invoke --id $CONTRACT -- pause_contract
```

**After (v0.2.0)**

```bash
NONCE=$(stellar contract invoke --id $CONTRACT -- admin_nonce)
stellar contract invoke --id $CONTRACT -- pause_contract --nonce "$NONCE"
```

Every admin call consumes the nonce, so a script that performs several admin operations must
re-read `admin_nonce()` before each one.

---

## 3. `upgrade` takes a `nonce`

The direct WASM swap is nonce-protected in the same way as the other admin operations.

**Before (v0.1.0)**

```rust
client.upgrade(&new_wasm_hash);
```

**After (v0.2.0)**

```rust
let nonce = client.admin_nonce();
client.upgrade(&new_wasm_hash, &nonce);
```

**Before (v0.1.0)**

```bash
stellar contract invoke --id $CONTRACT -- upgrade --new_wasm_hash $HASH
```

**After (v0.2.0)**

```bash
NONCE=$(stellar contract invoke --id $CONTRACT -- admin_nonce)
stellar contract invoke --id $CONTRACT -- upgrade --new_wasm_hash $HASH --nonce "$NONCE"
```

v0.2 also adds a two-step alternative that does not need a single-shot swap:
`propose_upgrade(new_wasm_hash, nonce)` → `execute_upgrade(nonce)`, with
`cancel_upgrade(nonce)` to abort. See the [upgrade guide](../upgrade-guide.md).

---

## 4. Token `burn` no longer takes an `admin` argument

In v0.1.0 only the contract admin could burn tokens, from any holder's balance. In v0.2 the
burn is authorised by the token holder, or by a spender with a sufficient allowance — the
same model as `transfer_from`.

**Before (v0.1.0)**

```rust
// admin-authorised burn, burns from an arbitrary account
client.burn(&admin, &holder, &amount);
```

**After (v0.2.0)**

```rust
// the holder burns their own tokens
client.burn(&holder, &amount);

// or a spender with an allowance burns on the holder's behalf
client.burn_from(&spender, &holder, &amount);
```

**Before (v0.1.0)**

```bash
stellar contract invoke --id $TOKEN -- burn --admin $ADMIN --from $HOLDER --amount 1000
```

**After (v0.2.0)**

```bash
stellar contract invoke --id $TOKEN -- burn --from $HOLDER --amount 1000
```

---

## 5. Token `mint` takes a new required `nonce` argument

`mint` is admin-only and is now nonce-protected, exactly like the stream contract's admin
operations.

**Before (v0.1.0)**

```rust
client.mint(&admin, &to, &amount);
```

**After (v0.2.0)**

```rust
let nonce = client.admin_nonce();
client.mint(&admin, &to, &amount, &nonce);
```

**Before (v0.1.0)**

```bash
stellar contract invoke --id $TOKEN -- mint --admin $ADMIN --to $TO --amount 1000000
```

**After (v0.2.0)**

```bash
NONCE=$(stellar contract invoke --id $TOKEN -- admin_nonce)
stellar contract invoke --id $TOKEN -- mint --admin $ADMIN --to $TO --amount 1000000 --nonce "$NONCE"
```

---

## 6. Token `approve` takes a new required `expiration_ledger` argument

Allowances now expire. `approve` records the last ledger sequence at which the allowance may
still be used; `transfer_from` reverts once the current ledger is past that point.

**Before (v0.1.0)**

```rust
client.approve(&owner, &spender, &amount);
```

**After (v0.2.0)**

```rust
// last ledger at which the allowance is still valid
client.approve(&owner, &spender, &amount, &expiration_ledger);
```

**Before (v0.1.0)**

```bash
stellar contract invoke --id $TOKEN -- approve --owner $OWNER --spender $SPENDER --amount 1000
```

**After (v0.2.0)**

```bash
stellar contract invoke --id $TOKEN -- approve \
  --owner $OWNER --spender $SPENDER --amount 1000 --expiration_ledger $LEDGER
```

The current allowance and its expiry can be read back with the new
`allowance(owner, spender) -> (i128, u32)` query.

---

## 7. `initialize` can only be called once

v0.1.0 allowed `initialize` to be called again, which silently overwrote the admin address —
the audit finding LOW-02. v0.2 reverts with `already initialized` on a second call.

**Before (v0.1.0)**

```rust
client.initialize(&admin); // could be called again to change the admin
```

**After (v0.2.0)**

```rust
client.initialize(&admin); // reverts with "already initialized" on a second call
```

To change the admin after deployment, use the two-step transfer introduced in v0.2:
`propose_admin(new_admin, nonce)` → `accept_admin(new_admin, nonce)`.

---

## 8. The `Stream` struct has two new fields

`Stream` gained `pending_accrual` and `low_balance_threshold`. Decoders that read the struct
positionally, or that validate the exact set of keys, must be updated.

**Before (v0.1.0)**

```json
{
  "id": "1",
  "employer": "GABC...",
  "employee": "GDEF...",
  "token": "CABC...",
  "deposit": "1000000",
  "withdrawn": "0",
  "rate_per_second": "10",
  "start_time": "1770000000",
  "stop_time": "0",
  "last_withdraw_time": "1770000000",
  "status": "Active",
  "locked": false
}
```

**After (v0.2.0)**

```json
{
  "id": "1",
  "employer": "GABC...",
  "employee": "GDEF...",
  "token": "CABC...",
  "deposit": "1000000",
  "withdrawn": "0",
  "rate_per_second": "10",
  "start_time": "1770000000",
  "stop_time": "0",
  "last_withdraw_time": "1770000000",
  "status": "Active",
  "pending_accrual": "0",
  "locked": false,
  "low_balance_threshold": "0"
}
```

| Field | Meaning |
|-------|---------|
| `pending_accrual` | Tokens accrued at the previous rate and not yet withdrawn. Populated by `update_rate` so the employee keeps the earnings from before the rate change, and paid out by the next `withdraw`. |
| `low_balance_threshold` | Remaining-deposit threshold below which a `low_balance` event is emitted after each withdraw. `0` disables the alert. |

## 9. Panic strings were replaced by `E###` error codes

v0.1.0 reverted with free-text messages such as `"stream not found"` or `"not the employer"`.
v0.2 uses stable error codes, so callers can match on the code instead of the prose.

**Before (v0.1.0)**

```rust
// matching on prose — breaks the moment the wording changes
if err.to_string().contains("not the employer") { /* ... */ }
```

**After (v0.2.0)**

```rust
// matching on the stable code
if err.to_string().contains("E018") { /* not the employer */ }
```

### Error codes added in v0.2

| Code | Constant | Meaning |
|------|----------|---------|
| E007 | `ERR_BELOW_MIN_DEPOSIT` | Deposit is below the admin-set minimum |
| E008 | `ERR_INVALID_RATE` | `rate_per_second` exceeds the maximum of 1,000,000,000 |
| E009 | `ERR_BAD_NONCE` | Invalid admin nonce |
| E010 | `ERR_NO_PENDING_ADMIN` | No pending admin has been proposed |
| E011 | `ERR_NOT_PENDING_ADMIN` | Caller is not the pending admin |
| E012 | `ERR_NOT_ADMIN` | Caller is not the contract admin |
| E013 | `ERR_CONTRACT_PAUSED` | The contract is paused |
| E014 | `ERR_EMPTY_PARAMS` | The batch parameter list is empty |
| E015 | `ERR_STREAM_NOT_FOUND` | The stream ID does not exist |
| E016 | `ERR_NOT_EMPLOYEE` | Caller is not the stream's employee |
| E017 | `ERR_STREAM_NOT_ACTIVE` | The stream is not Active or Exhausted |
| E018 | `ERR_NOT_EMPLOYER` | Caller is not the stream's employer |
| E019 | `ERR_STREAM_NOT_PAUSED` | The stream is not Paused |
| E020 | `ERR_STREAM_ALREADY_ENDED` | The stream is already Cancelled or Exhausted |
| E021 | `ERR_ADMIN_NOT_SET` | The admin has not been initialised |
| E022 | `ERR_STOP_TIME_PAST` | `stop_time` must be in the future |
| E023 | `ERR_AMOUNT_NOT_POSITIVE` | The amount must be positive |
| E024 | `ERR_BAD_PENDING_NONCE` | The nonce does not match the pending admin proposal |
| E025 | `ERR_NO_PENDING_UPGRADE` | No upgrade proposal exists |
| E026 | `ERR_DRAIN_NOT_PAUSED` | The contract must be hard-paused before an emergency drain |
| E027 | `ERR_NO_PENDING_DRAIN` | No emergency drain proposal exists |
| E028 | `ERR_NEW_EMPLOYER_IS_EMPLOYEE` | The new employer must differ from the employee |
| E029 | `ERR_BATCH_TOO_LARGE` | The batch contains more than 50 streams |

E001–E006 keep their meaning from v0.1.0 (`ERR_ZERO_RATE`, `ERR_ZERO_DEPOSIT`,
`ERR_REENTRANT`, `ERR_OVERFLOW`, `ERR_STREAM_CANCELLED`, `ERR_STREAM_EXHAUSTED`).

## 10. The event schema changed

### 10.1 Every topic is prefixed with the schema version

v0.1.0 published `("created", id)`; v0.2 publishes `("v1", "created", id)`. The first topic
element is now the schema version, so an indexer can route on it.

**Before (v0.1.0)**

```json
{ "topic": ["created", 1], "data": ["GABC...", "GDEF...", 10] }
```

**After (v0.2.0)**

```json
{ "topic": ["v1", "created", 1], "data": ["GABC...", "GDEF...", 10] }
```

**Before (v0.1.0)**

```javascript
function parseEvent(topic, data) {
  switch (topic[0]) {
    case "created": return { type: "stream_created", streamId: topic[1] };
    case "withdraw": return { type: "withdrawn", streamId: topic[1] };
  }
}
```

**After (v0.2.0)**

```javascript
function parseEvent(topic, data) {
  const version = topic[0];
  if (version !== "v1") {
    console.warn(`unknown event schema version: ${version}`);
    return null;
  }
  switch (topic[1]) {
    case "created": return { type: "stream_created", streamId: topic[2] };
    case "withdraw": return { type: "withdrawn", streamId: topic[2] };
  }
}
```

### 10.2 `stream_cancelled` now reports the cash-flow split

The `cancelled` event is new in v0.2. It carries the amount paid to the employee and the
amount refunded to the employer, so an indexer no longer has to replay the balance to
reconcile a cancellation.

```json
{ "topic": ["v1", "cancelled", 1], "data": ["300000", "700000"] }
```

### 10.3 New events

| Event | Topic | Data |
|-------|-------|------|
| `contract_initialized` | `["v1", "init"]` | `admin` |
| `stream_cancelled` | `["v1", "cancelled", <id>]` | `claimable_amount`, `refund_amount` |
| `rate_updated` | `["v1", "rate_upd", <id>]` | `old_rate`, `new_rate` |
| `upgrade_proposed` | `["v1", "upg_prop"]` | `wasm_hash`, `unlock_time` |
| `upgrade_executed` | `["v1", "upg_exec"]` | `wasm_hash` |
| `upgrade_cancelled` | `["v1", "upg_cncl"]` | — |
| `auto_topup_set` | `["v1", "at_set", <id>]` | `enabled` |
| `auto_topped_up` | `["v1", "at_up", <id>]` | `amount`, `total_topped_up` |
| `threshold_updated` | `["v1", "thresh_up", <id>]` | `old_threshold`, `new_threshold` |
| `receipt_transferred` | `["receipt", <id>]` | `from`, `to` |
| `stream_expired` | `["expired", <id>]` | — |
| `stream_transferred` | `["xfr_strm", <id>]` | `old_employer`, `new_employer` |
| `low_balance` | `["low_bal", <id>]` | `employer`, `remaining`, `threshold` |

The v0.1.0 events — `created`, `withdraw`, `status`, `topup`, `paused` — are unchanged apart
from the `v1` topic prefix. The full reference lives in
[docs/events-schema.md](../events-schema.md).

## 11. `create_streams_batch` is capped at 50 streams

v0.1.0 accepted a batch of any size. v0.2 rejects more than 50 entries with `E029`.

**Before (v0.1.0)**

```rust
// any number of streams was accepted
let ids = client.create_streams_batch(&employer, &params);
```

**After (v0.2.0)**

```rust
// split into chunks of at most 50
let mut ids = Vec::new(&env);
for chunk in params.chunks(50) {
    ids.append(&mut client.create_streams_batch(&employer, &chunk));
}
```

Note that each chunk is atomic on its own — a failure in one chunk does not roll back the
chunks that already succeeded. Verify the balances before submitting the next chunk if the
whole payroll run must be all-or-nothing.

---

## 12. Batch panic messages are prefixed with the stream index

`create_streams_batch` validates every entry before it transfers anything, and the failure
message names the offending entry. The message format changed.

**Before (v0.1.0)**

```
E001: rate_per_second must be greater than zero
```

**After (v0.2.0)**

```
stream[3]: E001: rate_per_second must be greater than zero
```

Strip the `stream[N]: ` prefix before comparing the message with a fixed string.

## Behaviour changes that are not signature changes

These do not break compilation, but they change what your integration observes.

| Change | Detail |
|--------|--------|
| `withdraw` auto-exhausts a stream | When `stop_time` has passed and nothing is claimable, the stream transitions to `Exhausted` instead of staying `Active`. |
| `top_up` guards against overflow | A deposit that would overflow `i128` now reverts with `E004` instead of wrapping. |
| `create_stream` emits a `low_balance` event | Emitted after a withdrawal when the remaining deposit drops below the stream's threshold. |
| `update_rate` preserves prior earnings | The amount accrued at the old rate is stored in `pending_accrual` and paid out by the next withdrawal. |
| Two-step admin transfer | `propose_admin` / `accept_admin` replace the old "call `initialize` again" pattern for changing the admin. |
| `transfer_stream` moves a stream to a new employer | The employee's receipt and the stream's ownership move together. |

## New in v0.2 (no changes required)

**Stream contract**

- `stream_status(stream_id)` — lightweight status query, no full struct loaded
- `get_streams_batch(stream_ids)` / `claimable_batch(stream_ids)` — batch reads
- `withdraw_all(employee)` — withdraw from every stream the employee holds
- `pause_stream_batch` / `resume_stream_batch` / `cancel_streams_batch` — bulk lifecycle operations
- `update_rate(employer, stream_id, new_rate)` — change a stream's rate mid-flight
- `transfer_stream(employer, stream_id, new_employer)` — hand a stream to a new employer
- `settle_stream(stream_id)` / `expire_streams(admin, stream_ids)` — finalise and expire streams
- `receipt_owner(stream_id)` / `transfer_receipt(from, to, stream_id)` — transferable receipts
- `save_template` / `create_stream_from_template` / `list_templates` — reusable stream templates
- `set_auto_topup` / `cancel_auto_topup` / `get_auto_topup_config` — recurring top-ups
- `set_low_balance_threshold(employer, stream_id, threshold)` — change the low-balance alert
- `streams_by_employee_paginated` / `streams_in_range` / `stream_count_by_employer` /
  `stream_count_by_employee` / `stream_count_by_token` — index queries
- `version()` — the contract version written by `migrate()`
- `is_paused()` / `get_pending_admin()` / `admin_nonce()` — admin state queries

**Token contract**

- `allowance(owner, spender)` — read an allowance and its expiry
- `burn_from(spender, from, amount)` — allowance-based burn
- `propose_admin` / `accept_admin` / `admin_nonce` — two-step admin transfer and replay protection
- `upgrade` / `migrate` — token contract upgrade path

## Migration checklist

- [ ] Add `--low_balance_threshold` / `None` to every `create_stream` call.
- [ ] Read `admin_nonce()` before every admin call and pass it to `pause_contract`,
      `unpause_contract`, `upgrade`, and the token `mint`.
- [ ] Drop the `admin` argument from token `burn` calls, or move to `burn_from`.
- [ ] Add `--expiration_ledger` to every token `approve` call.
- [ ] Stop calling `initialize` twice — use `propose_admin` / `accept_admin`.
- [ ] Update `Stream` decoders for `pending_accrual` and `low_balance_threshold`.
- [ ] Match on `E###` error codes instead of panic prose, and strip the `stream[N]: ` prefix.
- [ ] Route events on the `v1` schema prefix, and handle the new event names.
- [ ] Split `create_streams_batch` calls into chunks of 50.
- [ ] Re-test anything that depends on a stream staying `Active` after `stop_time` has passed.

---

## Rolling out the new contracts

The stream and token contracts are upgradeable in place through the Soroban WASM upgrade
path, so integrators do not have to redeploy:

1. Deploy the v0.2.0 WASM and record its hash.
2. Call `propose_upgrade(new_wasm_hash, nonce)` on the live contract, then
   `execute_upgrade(nonce)` once the timelock has passed.
3. The `migrate` hook runs after the swap; it is a no-op in the base v0.2 contract.
4. Point your client at the upgraded contract and work through the checklist above.

See the [upgrade guide](../upgrade-guide.md) for the full runbook and the
[key rotation runbook](../security/key-rotation.md) for rotating the admin keypair.
